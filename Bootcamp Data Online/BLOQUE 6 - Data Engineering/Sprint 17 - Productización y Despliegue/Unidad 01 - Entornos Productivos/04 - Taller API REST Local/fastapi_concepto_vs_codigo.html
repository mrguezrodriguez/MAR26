De la idea al código real

Las mismas cuatro operaciones, en pseudocódigo conceptual y en FastAPI de verdad.

💭 Concepto (pseudocódigo)
🐍 Cómo se escribe en FastAPI
GET
def get(*args):
    petición args http -> servidor <- json
@app.get("/pokemon/{nombre}")
def get_pokemon(nombre: str):
    return pokedex.get(nombre, {"error": "no encontrado"})
El "petición args http" es literalmente lo que hace @app.get: recibe la petición HTTP y te entrega nombre ya listo como argumento.
POST
def post(*args):
    petición args http -> servidor <- json
@app.post("/pokemon")
def post_pokemon(nombre: str, tipo: str):
    pokedex[nombre] = {"tipo": tipo}
    return {"mensaje": f"{nombre} añadido"}
Igual que get, pero aquí los args vienen en el cuerpo de la petición: son los datos que quieres crear/guardar.
DELETE
def delete(*args):
    petición args http -> servidor <- json
@app.delete("/pokemon/{nombre}")
def delete_pokemon(nombre: str):
    pokedex.pop(nombre, None)
    return {"mensaje": f"{nombre} eliminado"}
Mismo patrón otra vez: identifica el recurso por nombre, lo borra, devuelve confirmación en json.

@app.get("/")
def home():
    return {"mensaje": "Bienvenido a la Pokedex API"}
home es solo un GET a la ruta raíz "/" — el url y protocol del concepto ya están implícitos en la petición que llega.

Dónde está el wrapper aquí

El bloque de tu profe (petición args http -> servidor <- json) es exactamente lo que hace @app.get, @app.post y @app.delete por debajo: cada uno es un decorador que envuelve tu función (home, get_pokemon...) para encargarse de la parte repetitiva — recibir la petición HTTP, extraer los argumentos, y convertir lo que devuelvas en JSON.

Tú nunca escribes ese "petición -> servidor -> json" a mano: solo escribes la función con la lógica que te importa (buscar, guardar, borrar), y el decorador de FastAPI hace el resto — igual que @validar_argumentos hacía el resto por suma.
